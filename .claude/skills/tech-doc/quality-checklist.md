# Quality checklist for technical documents

Run this before asking for review. Fix every unchecked item, or say in the PR why it does not apply.

## Structure

- [ ] The title names the system and the document type ("Orders service: architecture")
- [ ] The metadata table is complete: status, owner, reviewers, last updated, version, related links, audience
- [ ] The summary answers, in five sentences: what, for whom, the decisions that shape it, status
- [ ] Every heading has content; no placeholder text; every "TBD" has an owner and appears under Open questions
- [ ] Six pages or fewer; details are linked (ADR, spec, runbook, dashboard), not pasted
- [ ] Risks, open questions and follow-ups are explicit, with owners and dates

## Writing

- [ ] Written for the named audience; terms are defined in the glossary on first use
- [ ] One idea per paragraph, concrete verbs, no filler adjectives ("robust", "seamless", "cutting-edge")
- [ ] Facts have sources (code paths, dashboards, documents); opinions are labelled as such
- [ ] Names match the code and the contracts, so readers can grep them
- [ ] Consistent tense, units and capitalisation; dates are ISO (YYYY-MM-DD); numbers have thousands separators

## Diagrams

- [ ] Each diagram answers one question and has a caption that states the takeaway
- [ ] 12 nodes or fewer; direction consistent (left to right for flows, top to bottom for layers)
- [ ] Derived from code and configuration, using the code's names; the system being described is visually distinct
- [ ] Data-flow diagrams label every arrow with the data and have a flow table (volume, format, classification)
- [ ] Sequence diagrams show the main failure path, not only the happy path
- [ ] Colour marks a role (system, external, store, async) using the theme's classes; nothing is coloured for decoration
- [ ] All Mermaid renders (`scripts/docs/confluence_publish.py <doc> --dry-run --strict`)

## Tables

- [ ] A header row; units in the header ("p95 (ms)", "throughput (req/s)")
- [ ] The source and date of the numbers stated next to the table
- [ ] No empty cells; use "n/a" or "–" deliberately
- [ ] Fixed decimals within a column; the same precision for comparable numbers

## Charts

- [ ] One measure per chart and one y-axis; never a dual-axis chart
- [ ] Title, axis labels with units, a legend for two or more series, an SLO or threshold line where one exists
- [ ] Generated by `scripts/docs/chart.py` (or the Mermaid chart from `perf_report.py`) from a committed CSV, never drawn by hand
- [ ] The same data is available as a table (`chart.py --table`)
- [ ] One theme for the whole document (`--theme`), the same in charts and rendered diagrams

## Numbers and evidence

- [ ] Every performance number comes with environment, version, load model, duration, date and tool
- [ ] Percentiles are named (p95, p99) and the method is stated; sample sizes are given
- [ ] Comparisons use the same conditions, or the differences are stated next to the comparison
- [ ] Excluded data (warm-up, outliers) is listed with the reason

## Confluence page

- [ ] Title unique in the space and searchable; parent page and labels agreed with the owner
- [ ] Table of contents at the top; metadata table published as Page Properties
- [ ] Diagrams rendered as images; relative links made absolute (`--link-base`)
- [ ] Checked in the browser after publishing: tables, panels, images, code blocks
- [ ] The page URL is recorded in the document's metadata table

## Before review

- [ ] A colleague, or Claude as the named audience, has read it and could answer the audience's first three questions
- [ ] The PR description links the document and the Confluence page; the change log row is added
